# Fly Pixel Game — передача для підключення мозку (Claude Code)

## 🧭 Почни звідси — огляд для нового чату (стан на 2026-09-15)

**Що це, в двох реченнях.** Один self-contained HTML-файл
(`fly-pixel-game.html`, ~4.8МБ, усі спрайти вшиті base64) — 2D pixel-art
симуляція мухи на робочому столі. Усі рішення мухи (куди йти, коли
їсти/чиститись/летіти/боятись/навчатись уникати небезпеку) виходять із
СПРАВЖНЬОГО нейронного конектома (клон [`snedea/flybrain`](https://github.com/snedea/flybrain),
~70 лумпованих груп нейронів), а не з `Math.random()` — щодо
`Math.random()`, що лишився, дивись нижче "Що НЕ реалізовано" й самі
коментарі `[BRAIN]` у коді.

**Як запустити.** Ніякої збірки. `python3 -m http.server 8080` у цій
теці → `http://localhost:8080/fly-pixel-game.html`, або просто відкрити
файл напряму в браузері (`file://` працює, крім хіба debug-серверних
речей). Детальніше — `README.md`.

**Файли репозиторію:**
- `fly-pixel-game.html` — уся гра, єдиний файл, що деплоїться
- `assets/*.png` — вихідні спрайт-аркуші (довідково, у рантаймі не читаються)
- `README.md` — коротко для GitHub-відвідувача, як запустити/задеплоїти
- `vercel.json` — маршрутизація деплою (`/` → `fly-pixel-game.html`)
- `HANDOFF.md` (цей файл) — стан проєкту, архітектура, дорожня карта
  (чекліст, що реалізовано/заплановано)
- `CHANGELOG.md` — повна хронологія розробки, сесія за сесією: кожен
  знайдений баг, кожне рішення з обґрунтуванням і перевіркою. Туди йти,
  коли потрібні деталі "чому саме так", а не просто "що є зараз".

**Архітектура за 30 секунд:** три шари — мозок (конектом, `BRAIN.*`) →
тіло (анімації/фізика/колізії) → сцена (фон/зони/сутності). Технічні
деталі конектома — нижче; повна хронологія кожного архітектурного
рішення — `CHANGELOG.md`.

**Методологія тестування, яку варто знати перед будь-якими змінами:**
змін перевіряються headless-браузером (не лише читанням коду) — драйвиться
`loop(t)` синтетичним годинником напряму з консолі/JS-виконання, а НЕ
справжнім `requestAnimationFrame`. ВАЖЛИВО: якщо повторно тестуєш на вже
завантаженій сторінці (не перезавантажуючи), обов'язково скинь
`lastHungerTick`/`lastBrainTick`/`nextPoopAt` до свіжого `tNow` на
початку кожного нового прогону — інакше застарілі таймери з попереднього
прогону дають катастрофічно неправильні результати (задокументовано як
знайдений і вирішений артефакт методології в `CHANGELOG.md`).

**Поточний фокус (2026-09-15):** підготовка до деплою на GitHub + Vercel
(мобільна адаптація вже додана в код; `vercel.json`/`README.md`/
`.gitignore` підготовлені; git-репозиторій і сам деплой — наступний крок,
див. "Деплой" у дорожній карті нижче).

**Стратегія на майбутнє (сказано користувачем, не вигадано):** ЦЕЙ
репозиторій — "легка" версія (~70 груп нейронів) і лишається окремою
продакшн-версією. Паралельно, окремим проєктом, планується повна модель
на всіх ~130k+ нейронах (FlyWire) з реал-тайм візуалізацією активності
нейронів, на окремому хостингу — вона НЕ замінює цю версію, а існує поруч.

## Технічні деталі конектома (не дублюється вище)

Мозок — дослівний перенос `js/constants.js` (вагова таблиця) і "легасі"
шляху `js/connectome.js` (`dendriteAccumulate → fireNeuron → runconnectome`)
проєкту [`snedea/flybrain`](https://github.com/snedea/flybrain) (MIT), той
самий такт 500мс (`BRAIN_TICK_MS`/`runBrainTick`), що й в оригіналі.

Свідомо НЕ підключено `js/brain-worker-bridge.js` + `js/sim-worker.js` +
`data/connectome.bin.gz` (повна ~139k-нейронна модель через Web Worker,
~12МБ бінарних даних FlyWire): цей шлях вимагає HTTP-сервера (`fetch` +
`new Worker()` не працюють при відкритті файлу напряму як `file://`), а
гра свідомо self-contained (спрайти теж вшиті base64). "Легасі"
~70-групова модель — той самий справжній конектом-двигун проєкту, просто
синхронний і без зовнішніх залежностей. Повна модель — окремий майбутній
проєкт (див. дорожню карту вище).

## Калібрувальні дані спрайтів (важливо для будь-яких змін анімації)

Кожен спрайт-аркуш має свою специфіку нарізки — **не всі кадри рівномірні
за шириною**. Дивіться коментарі біля `walkSheet`, `idleSheet`,
`groomFramesA`, `walkDiagFrames`, `walkDiag2Frames`, `flightFrames` у коді:
для кожного там або спільний масштаб на весь аркуш (walk/idle — рівномірні
кадри), або індивідуальний масштаб+анкор на кожен кадр (groom/діагоналі —
дуже нерівномірні через рух лапок/крил). Ці межі виведені аналізом
альфа-каналу вихідних PNG (шукали проміжки між фігурами), а не рівним
поділом — рівний поділ кілька разів спричиняв баги "протікання" кадрів.

Для flight-кадрів є додатковий нюанс: НЕ рахуйте масштаб окремо на кожен
кадр за bodyH, коли крила міняють форму (не висоту) — це "роздуває" тіло
візуально. Використано єдиний спільний масштаб (`FLIGHT_REF_BODY_H`) для
всього аркуша, з індивідуальними лише центрами позиції.

Той самий per-frame-anchor підхід (`groomFrame()`) повторно використаний
пізніше для таргана й лазіння — деталі й виміряні координати кожного
конкретного аркуша шукай у `CHANGELOG.md`.

  ще не почата)

- Навчання таргана (`MB_KC_ROACH`) — за прямою вказівкою користувача,
  свідомо востаннє в черзі: лише ПІСЛЯ підтвердження, що патерн навчання
  на чашці/проводі справді працює довше, І після розділення джерел
  `VIS_LC` (наразі стіни/таргана/клік усі штовхають той самий спільний
  нейрон — без розділення навчений страх від таргана хибно узагальнився б
  на звичайні стіни). Див. пам'ять `fly-learning-roadmap`.

  голоду) — кавова пляма поки лише частково впливає на `hunger`
  (`COFFEE_HUNGER_RELIEF`), справжня спрага з'явиться разом із майбутнім
  джерелом чистої води (сам користувач це відклав: "згодом додамо й
  джерело чистої води")
